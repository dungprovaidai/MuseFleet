# Muse sign-in redirects in WKWebView

Research performed: 2026-11-28. Scope: public Muse landing HTML and first-party JavaScript assets, current public Meta/Apple developer documentation, and the supplied MuseFleet screenshots. No form was submitted; no authenticated page, account data, cookie, token, OTP, private API or device traffic was accessed.

## Findings

1. **The two screenshots indicate different states.** The first screenshot shows `WebKit error 102`, which alone does not identify a root cause. The next screenshot displays MuseFleet's own message that it cancelled a main-frame redirect. In the current source that message can only be produced when the navigation delegate marks a main-frame policy rejection before reporting WebKit 102. That is direct evidence the allowlist caused the displayed failure, not a generic network diagnosis.

2. **Muse's public frontend gives a first-party login-origin lead.** The HTML at `https://muse.ai/` loads hashed JavaScript assets from the same first-party origin. The asset [`0tmjjrf9k1ayz.js`](https://muse.ai/_next/static/immutable/chunks/0tmjjrf9k1ayz.js), retrieved at the research date, includes a fixed OIDC base URL `https://auth.meta.com/oidc`; the corresponding helper insists on HTTPS, no user/password/port and an exact `auth.meta.com` or explicitly patterned OIDC origin. Its URL-return validator accepts the auth origin on `/auth_platform`, `/checkpoint(s)` and validates `www.facebook.com` / `www.instagram.com` only on `/auth_platform`. A related asset [`0tumyugx4k7kx.js`](https://muse.ai/_next/static/immutable/chunks/0tumyugx4k7kx.js) references `https://auth.meta.com/form/?form_id=1195697011444585` as a terms URL. These observations establish that the currently served public client recognizes those domains/routes; they do **not** prove which route the user's session actually follows, that every route is used for sign-in, or that Meta guarantees embedded WKWebView support.

3. **Official product docs corroborate identity-provider context, not embedded-webview compatibility.** Meta's [Muse onboarding guide](https://www.meta.com/help/superintelligence/1331373868832401/) says Muse web and app use a Meta Account and that a person can create one using Facebook, Instagram, email or phone. Meta's [Facebook Login manual flow](https://developers.facebook.com/documentation/facebook-login/guides/advanced/manual-flow/) documents HTTPS redirects and `www.facebook.com` OAuth endpoints for an application implementing Facebook Login. That separate developer integration is not a Muse sign-in contract and must not be used to infer that arbitrary Facebook pages belong in MuseFleet's allowlist.

4. **System authentication is not an automatic fix for a named WebKit profile.** Apple documents that `WKWebsiteDataStore(forIdentifier:)` provides a persistent per-profile store. [`ASWebAuthenticationSession`](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession) is a separate system-managed authentication session that returns a service callback URL; Apple documents no way to attach a MuseFleet `WKWebsiteDataStore` to it or to seed that profile afterward. Copying Safari cookies, collecting credentials, or moving session tokens across stores is therefore not an acceptable workaround and would break account isolation.

5. **Scope of the 0.1.3 fix.** It admits HTTPS at exact host `auth.meta.com`, plus exact `www.facebook.com` / `www.instagram.com` hosts only on the public client's `/auth_platform` route. It still rejects deceptive suffixes, non-HTTPS, credentials, nonstandard ports, unrelated Meta/Google/Apple domains and the Facebook/Instagram site outside that auth path. When another main-frame destination is cancelled, the UI reports the sanitized hostname only; it does not display path, query or fragment. The UI test checks this redaction and policy tests reject representative lookalikes. These tests exercise local policy, not a real OIDC transaction.

## Remaining checks

- Install a properly signed build on the user's iPhone and retry the normal Muse web login. Record only whether the login page advances, the app build and any blocked hostname. Never send a sign-in URL, query, code, email, phone, screenshot of credentials or token.
- If the UI still shows a blocked hostname, compare the hostname/path against a fresh public Muse build and official guidance before adding it. Do not wildcard `*.meta.com`, `*.facebook.com`, `*.instagram.com` or `*.muse.ai`.
- If authentication returns to Muse but the page remains blank, collect only the safe WebKit error domain/code and whether the page arrived through a popup. Test the same URL on Safari only as a comparison; Safari success is not evidence that cookies or identity transfer to MuseFleet.
- Only the account owner can establish actual device/session compatibility; public HTML, static asset strings, simulator tests and a successful IPA build do not substitute for that test.
