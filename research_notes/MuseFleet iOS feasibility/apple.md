# Apple iOS 17 feasibility for MuseFleet

Research date: 2026-11-28. Target: native iOS 17+ with account-specific persistent WebKit stores. This is source research from Windows, not an Apple build, simulator run, device test, or verification of Muse's website. The repository explicitly requires that distinction. — [Engineering contract](../../AGENTS.md)

Evidence labels used throughout:

- **VERIFIED**: the researcher directly checked the cited source text or source metadata. This label describes the evidence check, never successful execution of an iOS feature.
- **DOCUMENTED**: Apple or WebKit describes the API or behavior; MuseFleet has not demonstrated it on an Apple runtime.
- **UNVERIFIED**: a proposed integration, site behavior, or runtime result still needs direct testing.
- **UNSUPPORTED**: the proposed product guarantee is outside the documented iOS 17 capability or conflicts with its constraints.
- **BLOCKED**: the necessary verification cannot be performed in this Windows research environment, or a source could not be read.

Dynamic Apple documentation was read through its official DocC JSON at `https://developer.apple.com/tutorials/data/documentation/<symbol-or-article>.json`. The initializer, deletion, and enumeration metadata each explicitly report `iOS` / `introducedAt: "17.0"`. Declarations below reflect the documentation retrieved on the research date; concurrency annotations in the current SDK need an actual Xcode compile before being called build-verified. — **VERIFIED, source inspection only**: [Initializer JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/init(foridentifier:).json), [Deletion JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:).json), [Enumeration JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/fetchalldatastoreidentifiers(_:).json)

## 1. Can iOS 17 persist isolated accounts, and how is an account store deleted?

### Takeaway

**DOCUMENTED:** iOS 17 provides identified persistent stores intended for profile browsing. Persist each account UUID and assign its identified store to the configuration before constructing any associated web view. Whole-store deletion is also available in iOS 17 and requires releasing all web views using that store first. — [WKWebsiteDataStore](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), [Deletion](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:))

### Cited Findings

| Exact public Swift API | iOS availability | Classification and evidence |
| --- | --- | --- |
| `init(forIdentifier identifier: UUID)` | 17.0+ | **DOCUMENTED.** Returns the persistent store for the identifier, creating it if absent. Apple explicitly describes using it for a profile. [Apple](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:)) |
| `class func remove(forIdentifier identifier: UUID, completionHandler: @escaping @MainActor @Sendable ((any Error)?) -> Void)` | 17.0+ | **DOCUMENTED.** Deletes the identified store, reporting an error if removal cannot complete. This is a type method, not an instance `delete` method. [Apple JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:).json) |
| `class func remove(forIdentifier identifier: UUID) async throws` | 17.0+ | **DOCUMENTED.** Async form of whole-store removal. Call `try await WKWebsiteDataStore.remove(forIdentifier: id)`. [Apple JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:).json) |
| `class func fetchAllDataStoreIdentifiers(_ completionHandler: @escaping @MainActor @Sendable ([UUID]) -> Void)` | 17.0+ | **DOCUMENTED.** Enumerates existing stores that have identifiers. [Apple](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/fetchalldatastoreidentifiers(_:)) |
| `class var allDataStoreIdentifiers: [UUID] { get async }` | 17.0+ | **DOCUMENTED.** The imported async API is a property: `let ids = await WKWebsiteDataStore.allDataStoreIdentifiers`. Do not invent `fetchAllDataStoreIdentifiers() async`. [Apple JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/fetchalldatastoreidentifiers(_:).json) |
| `var websiteDataStore: WKWebsiteDataStore { get set }` on `WKWebViewConfiguration` | 9.0+ | **DOCUMENTED.** An unset property uses the default persistent store. Explicitly set it for every account web view. [Apple](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/websitedatastore) |
| `func removeData(ofTypes dataTypes: Set<String>, modifiedSince date: Date) async` | Underlying API 9.0+; usable on the iOS 17 target | **DOCUMENTED.** Clears selected types of data from that store; it does not have the semantics of deleting the identified store. The callback form ends in `completionHandler: @escaping @MainActor @Sendable () -> Void`, with no error parameter. [Apple JSON](https://developer.apple.com/tutorials/data/documentation/webkit/wkwebsitedatastore/removedata(oftypes:modifiedsince:completionhandler:).json) |

- **DOCUMENTED:** `WKWebsiteDataStore` manages cookies, disk and memory caches, and other website data. Apple distinguishes default persistent storage, nonpersistent memory-only storage, and identified persistent storage for profile browsing. Configure the store before creating the `WKWebView`. — [Apple overview](https://developer.apple.com/documentation/webkit/wkwebsitedatastore)
- **DOCUMENTED:** The initializer can raise an exception for an invalid identifier. The retrieved reference does not enumerate all invalid UUID values. A normally generated, persisted account `UUID()` fits the public API; do not describe this initializer as Swift `throws`. — [Apple initializer](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:))
- **DOCUMENTED:** Apple's removal discussion says: “Release any `WKWebView` instances using the data store before you call this method.” A stopped or hidden web view has not necessarily been released. — [Apple deletion](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:))
- **DOCUMENTED:** Reusing the same identifier retrieves that identified store; a new identifier creates a different profile store. Persistence is storage on disk, not a promise that the server will keep a login valid indefinitely. — [Apple initializer](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:)), [Apple overview](https://developer.apple.com/documentation/webkit/wkwebsitedatastore)

The documented construction sequence is the following. This is illustrative Swift, not a compiled test result. — [Apple configuration](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/websitedatastore), [Apple initializer](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:))

```swift
let configuration = WKWebViewConfiguration()
configuration.websiteDataStore = WKWebsiteDataStore(forIdentifier: account.id)
let webView = WKWebView(frame: .zero, configuration: configuration)
```

### Inferences

- **UNVERIFIED integration:** Use `AccountProfile.id` as the stable store identifier across launches and session-cache eviction. Evicting a live browser session should release its web views, without invoking whole-store removal. The app's three-session memory cap need not delete the other accounts' persistent stores. — [Apple identified stores](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:)), [BrowserPool contract](../../AGENTS.md)
- **UNVERIFIED integration:** Account deletion must close popups, detach account views from SwiftUI/UIKit, remove strong references from the session cache, and prevent concurrent recreation of that account's session before awaiting store removal. Every popup also counts as a `WKWebView` for Apple's release requirement. Only commit successful deletion to account metadata after removal succeeds, or preserve a recoverable failure state; otherwise data may remain on disk after the UI claims deletion. — [Apple deletion precondition/error behavior](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/remove(foridentifier:completionhandler:)), [Browser/account contract](../../AGENTS.md)
- **UNVERIFIED integration:** Distinguish “clear website data” from “delete account.” Clearing all types since `.distantPast` can use the account store's `removeData(ofTypes:modifiedSince:)` with `WKWebsiteDataStore.allWebsiteDataTypes()`. Deleting the identified container uses the throwing class method. Do not report a nonexistent error result from the nonthrowing clear-data completion handler. — [Apple clear-data API](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/removedata(oftypes:modifiedsince:completionhandler:)), [Apple data-store API list](https://developer.apple.com/documentation/webkit/wkwebsitedatastore)
- **UNVERIFIED integration:** The identified-store boundary is the supported profile-storage design, not proof that Muse accepts every embedded login flow. Do not copy cookies, extract tokens, or substitute the default store when a login fails. Those substitutions violate the project contract and undo the intended profile boundary. — [Apple profile design](https://developer.apple.com/documentation/webkit/wkwebsitedatastore), [Credential and isolation contract](../../AGENTS.md)

### Gaps

- **BLOCKED:** No Xcode, iOS simulator, or iPhone was available for this Windows assignment. The required cookie/site-storage isolation fixture, persistence across relaunch, store deletion failure/retry behavior, and current-SDK compilation have not run. This is an environment limitation, not evidence that the documented APIs fail. — [Repository validation requirements](../../AGENTS.md)
- **UNVERIFIED:** Actual Muse login/session expiry, identity-provider policies, simultaneous account behavior, and server behavior after account-store recreation were not tested. Apple's profile API documentation cannot establish a third-party website's compatibility. — [Scope of Apple's profile API](https://developer.apple.com/documentation/webkit/wkwebsitedatastore/init(foridentifier:))

## 2. What constraints apply to popups, authentication, and downloads?

### Takeaway

**DOCUMENTED:** Popup support must return a new web view built from WebKit's supplied configuration, and downloads must use the WebKit download/delegate lifecycle. **UNVERIFIED:** Muse's login popups, cross-site redirects, and generated downloads work under these APIs; they require site-specific and device evidence. — [Apple popup delegate](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:createwebviewwith:for:windowfeatures:)), [Apple WKDownload](https://developer.apple.com/documentation/webkit/wkdownload)

### Cited Findings

- **DOCUMENTED, iOS 8.0+:** The popup callback is `webView(_:createWebViewWith:for:windowFeatures:) -> WKWebView?` on `WKUIDelegate`. Apple states: “The web view returned must be created with the specified configuration. WebKit loads the request in the returned web view.” Returning `nil` declines the new view. Creating a replacement configuration is not the documented popup flow. — [Apple popup delegate](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:createwebviewwith:for:windowfeatures:))
- **DOCUMENTED, iOS 8.0+:** `WKPreferences.javaScriptCanOpenWindowsAutomatically` controls opening windows without user interaction, and defaults to `false` on iOS. This is different from handling a window requested by a user gesture. — [Apple popup preference](https://developer.apple.com/documentation/webkit/wkpreferences/javascriptcanopenwindowsautomatically)
- **DOCUMENTED:** WebKit calls `webViewDidClose(_:)` when the DOM window closes. The host app should remove that web view from the hierarchy and update its UI. — [Apple close callback](https://developer.apple.com/documentation/webkit/wkuidelegate/webviewdidclose(_:))
- **DOCUMENTED:** `WKNavigationDelegate` permits navigation policy decisions and receives authentication challenges. `webView(_:didReceive:completionHandler:)` takes `URLAuthenticationChallenge` and a completion handler receiving `(URLSession.AuthChallengeDisposition, URLCredential?)`. This is a network authentication-challenge API, not an API that signs a user into a website's JavaScript login form. — [Apple navigation delegate](https://developer.apple.com/documentation/webkit/wknavigationdelegate), [Apple challenge callback](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:didreceive:completionhandler:))
- **DOCUMENTED:** `ASWebAuthenticationSession` starts a browser-mediated authentication flow and returns a service callback URL to the app. `prefersEphemeralWebBrowserSession`, available on iOS 13+, requests that cookies and other browsing data not be shared with the normal browser session; Safari respects this request. The property defaults to `false` and must be set before `start()`. It is not an API parameter accepting an account's `WKWebsiteDataStore`. — [Apple authentication session](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession), [Apple ephemeral-session setting](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession/prefersephemeralwebbrowsersession)
- **DOCUMENTED:** Intelligent Tracking Prevention has been enabled by default in all `WKWebView` apps since iOS 14. Opting into `WKAppBoundDomains` changes access to JavaScript injection, message handlers, and cookie APIs. With `limitsNavigationsToAppBoundDomains = true`, navigating the top-level frame outside the app-bound set fails. The app-bound list supports up to ten domains. — [WebKit, App-Bound Domains](https://webkit.org/blog/10882/app-bound-domains/)

| Download API / responsibility | Availability and documented behavior |
| --- | --- |

[Action callback](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:navigationaction:didbecome:)), [Response callback](https://developer.apple.com/documentation/webkit/wknavigationdelegate/webview(_:navigationresponse:didbecome:)) |
| `weak var delegate: (any WKDownloadDelegate)?` | **DOCUMENTED, iOS 14.5+.** The download delegate is weak. Its owner must remain alive for callbacks to be useful. [Apple](https://developer.apple.com/documentation/webkit/wkdownload/delegate) |

### Inferences

- **UNVERIFIED integration:** For a permitted popup, inspect that WebKit's supplied configuration uses the originating account's identifier, construct the popup with that exact configuration, and apply the same navigation/privacy delegates. Do not silently create it with a default store or flatten every `window.open` into a navigation of the parent: replacing a popup can break opener/callback behavior. Check opener communication in the real authentication flow. — [Apple popup configuration requirement](https://developer.apple.com/documentation/webkit/wkuidelegate/webview(_:createwebviewwith:for:windowfeatures:)), [Account isolation contract](../../AGENTS.md)
- **UNVERIFIED integration:** A strict Muse-only navigation allowlist can block a legitimate identity-provider redirect or popup. Add only login hosts verified against the actual official flow, with explicit user-visible handling for unsupported navigation. Neither accepting arbitrary hosts nor moving the login to an external browser proves that it will authenticate the original account store. — [Apple navigation policy role](https://developer.apple.com/documentation/webkit/wknavigationdelegate), [Apple browser-mediated authentication model](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession), [HTTPS allowlist contract](../../AGENTS.md)
- **UNVERIFIED integration:** `ASWebAuthenticationSession` is not a drop-in way to seed a `WKWebsiteDataStore` login. A supported service callback/exchange would need a service-owned integration design; do not extract or copy browser credentials to manufacture one. Provider refusal of an embedded user agent must remain a compatibility failure, not trigger an authentication bypass. — [Apple callback-based session model](https://developer.apple.com/documentation/authenticationservices/aswebauthenticationsession), [No credential collection or bypass contract](../../AGENTS.md)
- **UNVERIFIED integration:** App-Bound Domains can block both required login navigation and the DOM observer's JavaScript/message handlers if configured without understanding the opt-in behavior. Do not add that key as a cosmetic security setting. Review the actual host flow before choosing it; it does not replace `URLPolicy`. — [WebKit opt-in restrictions and examples](https://webkit.org/blog/10882/app-bound-domains/), [URLPolicy contract](../../AGENTS.md)
- **UNVERIFIED integration:** Keep authenticated resource downloads inside `WKDownload` rather than extracting cookies to a separate downloader. Treat `suggestedFilename` as untrusted display input: reduce it to a safe filename, choose a unique app-sandbox destination, and prevent overwrite/path traversal. Validate HTTP download redirects separately because WebKit's default is to follow them all; the main-frame navigation delegate alone is not the complete redirect policy. — [Apple destination requirements](https://developer.apple.com/documentation/webkit/wkdownloaddelegate/download(_:decidedestinationusing:suggestedfilename:completionhandler:)), [Apple redirect behavior](https://developer.apple.com/documentation/webkit/wkdownloaddelegate/download(_:willperformhttpredirection:newrequest:decisionhandler:)), [No cookie collection contract](../../AGENTS.md)
- **UNVERIFIED integration:** Publish `downloadedFile` only after `downloadDidFinish`, surface failures, and retain the session's delegate owner until the operation completes or is cancelled. Do not promise that `WKDownload` survives suspension or force quit merely because native background `URLSession` has a separate background-transfer mechanism. — [Apple finish/failure callbacks](https://developer.apple.com/documentation/webkit/wkdownloaddelegate), [Weak delegate](https://developer.apple.com/documentation/webkit/wkdownload/delegate), [Apple background strategy distinction](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)

### Gaps

- **UNVERIFIED:** No Muse popup, identity-provider page, cookie policy interaction, blob export, signed download URL, CDN redirect, or filename behavior was exercised. Official API support for a blob response does not prove that every site-specific generated export works. — [Apple destination/response API scope](https://developer.apple.com/documentation/webkit/wkdownloaddelegate/download(_:decidedestinationusing:suggestedfilename:completionhandler:))
- **BLOCKED:** Device checks for popup account isolation, WebKit-supplied popup configuration, login opener callbacks, download cancellation during account deletion, and sharing a completed file remain outstanding. — [Repository runtime validation requirement](../../AGENTS.md)

## 3. Which notification and background behaviors can the app honestly offer?

### Takeaway

**DOCUMENTED:** Local notifications can present events the app has already observed; native APNs requires a provider server and an actual event source. App refresh and silent pushes are opportunistic and time limited. **UNSUPPORTED:** continuous background WebView monitoring or treating iOS 17's Home Screen Web Push as a push subscription inside MuseFleet's embedded `WKWebView`. — [Local notifications](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app), [Native push architecture](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server), [Background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app), [Web Push scope](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers)

### Cited Findings

#### Local notifications and native account routing

- **DOCUMENTED:** Request user-facing notification permission in context with `let granted = try await UNUserNotificationCenter.current().requestAuthorization(options: [.alert, .sound, .badge])`; the result is `Bool`. Inspect `await center.notificationSettings()` and `authorizationStatus` again because users can change permission in Settings. Repeated authorization requests do not repeatedly show the prompt. — [Apple authorization guide](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications), [Exact authorization API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/requestauthorization(options:completionhandler:))
- **DOCUMENTED:** Create `UNMutableNotificationContent`, a `UNNotificationRequest(identifier:content:trigger:)`, and call `try await center.add(request)`. A `nil` trigger delivers immediately. This API schedules local notifications only, not remote notifications. The system can present an already scheduled notification while the app is not running. — [Apple local scheduling guide](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app), [Exact add API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/add(_:withcompletionhandler:))
- **DOCUMENTED:** Notification content provides `userInfo` for app-specific routing data. Handle foreground delivery with `userNotificationCenter(_:willPresent:withCompletionHandler:)`; handle notification interaction with `userNotificationCenter(_:didReceive:withCompletionHandler:)`. The async variants are `userNotificationCenter(_:willPresent:) async -> UNNotificationPresentationOptions` and `userNotificationCenter(_:didReceive:) async`. Callback variants must invoke their completion handlers. — [Apple notification handling guide](https://developer.apple.com/documentation/usernotifications/handling-notifications-and-notification-related-actions), [Foreground API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/usernotificationcenter(_:willpresent:withcompletionhandler:)), [Response API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate/usernotificationcenter(_:didreceive:withcompletionhandler:))
- **DOCUMENTED, iOS 16.0+:** Set the native application icon badge with `try await center.setBadgeCount(count)`. The completion-handler form is `setBadgeCount(_:withCompletionHandler:)` and can report an error. — [Apple badge API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/setbadgecount(_:withcompletionhandler:))
- **DOCUMENTED:** Provisional permission delivers trial notifications quietly in Notification Center rather than promising a banner, sound, or lock-screen alert. Native notification presentation remains subject to the person's authorization/settings; WebKit also documents Focus integration for Home Screen notifications. — [Apple provisional authorization](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications), [WebKit Focus behavior](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)

#### Native APNs and silent push

- **DOCUMENTED:** Native remote notifications require a provider server, APNs, a device, and the receiving app. The server decides when an event exists and generates the push request; APNs handles transport/presentation. Enable Push Notifications, the App ID service, and the signing entitlement `aps-environment`. Call `UIApplication.shared.registerForRemoteNotifications()`, receive `application(_:didRegisterForRemoteNotificationsWithDeviceToken:)`, and handle `application(_:didFailToRegisterForRemoteNotificationsWithError:)`. — [Apple architecture](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server), [Apple registration and entitlements](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)
- **DOCUMENTED:** A native APNs device token identifies this app on this device, not each embedded Muse account. Each app must obtain its own token and forward it securely to its provider. Apple says not to cache the device token locally; obtain the current token at launch. Account association is provider/application logic. Native APNs provider authentication uses server-side token-based or certificate-based trust over HTTP/2 and TLS. — [Apple device tokens and account association](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns), [Apple provider setup](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server)
- **DOCUMENTED:** APNs makes every effort to deliver pushes; notifications may be held for an offline device or coalesced for the same bundle ID. Do not promote APNs to an unconditional instant-delivery guarantee. — [Apple APNs behavior](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server)
- **DOCUMENTED:** Background pushes are low priority, do not display an alert/sound/badge, are not guaranteed, and may be throttled. Apple advises not attempting more than two or three per hour, rather than offering a fixed polling quota. Enable the `remote-notification` background mode. Use `aps: {"content-available": 1}`, `apns-push-type: background`, and `apns-priority: 5`. — [Apple background push guide](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app)
- **DOCUMENTED:** Background notification handling has up to 30 seconds. The callback is `application(_:didReceiveRemoteNotification:fetchCompletionHandler:)`; call its completion handler promptly. iOS may hold an update, discard an older held update in favor of a newer one, and discard held notifications when the app is force quit or killed. — [Apple background push lifecycle](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app), [Apple delegate API](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/application(_:didreceiveremotenotification:fetchcompletionhandler:))
- **DOCUMENTED:** The app delegate reference explicitly says the system does not automatically launch an app for this notification handling after the user force-quits it. It says the user must relaunch the app or restart the device before automatic launches are attempted again. This restriction concerns executing the app; it is not a statement that every system-displayed alert notification is suppressed. — [Apple force-quit restriction](https://developer.apple.com/documentation/uikit/uiapplicationdelegate/application(_:didreceiveremotenotification:fetchcompletionhandler:)), [Apple remote notification presentation architecture](https://developer.apple.com/documentation/usernotifications/setting-up-a-remote-notification-server)

#### BGAppRefresh and suspension

- **DOCUMENTED, iOS 13.0+:** `BGAppRefreshTask` handles a short content refresh. Enable the `fetch` background mode and add task identifiers to `BGTaskSchedulerPermittedIdentifiers`. Register handlers with `BGTaskScheduler.shared.register(forTaskWithIdentifier:using:launchHandler:)` before launch completes. Register each identifier once: Apple's reference warns that a second registration kills the app. — [Apple refresh class](https://developer.apple.com/documentation/backgroundtasks/bgapprefreshtask), [Apple setup guide](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app), [Apple registration API](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/register(fortaskwithidentifier:using:launchhandler:))
- **DOCUMENTED:** For the iOS 17 baseline, create `BGAppRefreshTaskRequest(identifier:)`, optionally set `earliestBeginDate`, and call `try BGTaskScheduler.shared.submit(request)`. A repeated request with the same queued identifier replaces the previous request. Apple's live API reference allows one pending refresh request, not one request for every account. — [Apple scheduling example](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app), [Apple submit API](https://developer.apple.com/documentation/backgroundtasks/bgtaskscheduler/submit(_:))
- **DOCUMENTED:** `earliestBeginDate` means “not before,” not “at.” Apple explicitly does not guarantee launch at that date. Its example's fifteen-minute value is an example minimum start delay, not a fifteen-minute repeating timer. The system chooses when to launch and grants up to 30 seconds of refresh runtime. — [Apple earliest date](https://developer.apple.com/documentation/backgroundtasks/bgtaskrequest/earliestbegindate), [Apple strategy/runtime limits](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)
- **DOCUMENTED:** Install `task.expirationHandler` to cancel/clean up promptly, and call `task.setTaskCompleted(success:)` when finished. Expiration can happen before all allocated time is used. Reschedule a future request if recurring refresh is appropriate; a task request is not a permanent worker. — [Apple expiration handler](https://developer.apple.com/documentation/backgroundtasks/bgtask/expirationhandler), [Apple completion API](https://developer.apple.com/documentation/backgroundtasks/bgtask/settaskcompleted(success:)), [Apple rescheduling example](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app)
- **DOCUMENTED:** Adding `BGTaskSchedulerPermittedIdentifiers` disables the legacy `application(_:performFetchWithCompletionHandler:)` and `setMinimumBackgroundFetchInterval(_:)` path on iOS 13+. Do not configure modern task scheduling while assuming the legacy periodic fetch handler still runs. — [Apple configuration caveat](https://developer.apple.com/documentation/uikit/using-background-tasks-to-update-your-app)
- **DOCUMENTED:** UIKit normally moves offscreen scenes from background to suspended and may disconnect them to reclaim resources. `beginBackgroundTask(withName:expirationHandler:)` only obtains limited time to finish critical foreground work; it is not an indefinite execution entitlement. — [Apple lifecycle](https://developer.apple.com/documentation/uikit/managing-your-app-s-life-cycle), [Apple background strategies](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)

#### Web Push versus an embedded WKWebView

- **DOCUMENTED:** Apple specifies Web Push for Home Screen web apps in iOS 16.4+, and Safari webpages on macOS 13+. WebKit's iOS announcement likewise scopes iOS support to web apps added to the Home Screen. A native app icon containing a `WKWebView` does not turn that embedded page into a Home Screen web app. — [Apple supported contexts](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [WebKit iOS support announcement](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
- **DOCUMENTED:** Home Screen web apps can request push permission in direct response to a user gesture. The documented iOS 17-era implementation uses Push API, Notifications API, and Service Workers. The site/server must support subscription endpoints and notification payloads. Web Push uses Apple's push service but does not require Apple Developer Program membership. This is separate from registering a native application bundle and native device token. — [WebKit Web Push prerequisites](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Apple web push implementation](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [Native registration](https://developer.apple.com/documentation/usernotifications/registering-your-app-with-apns)
- **DOCUMENTED:** Safari does not support invisible Web Push as a source of silent JavaScript runtime. A received push must promptly result in a user-visible notification or permission can be revoked. A badge update alone does not satisfy that requirement. — [Apple visibility requirement](https://developer.apple.com/documentation/usernotifications/sending-web-push-notifications-in-web-apps-and-browsers), [WebKit badge/push distinction](https://webkit.org/blog/14112/badging-for-home-screen-web-apps/)
- **DOCUMENTED:** WebKit explicitly states that the iOS 16.4 Home Screen Badging API is not exposed in any app using `WKWebView`, nor in ordinary iOS browser tabs. Use the native `UNUserNotificationCenter` badge API for MuseFleet's icon. — [WebKit context restriction](https://webkit.org/blog/14112/badging-for-home-screen-web-apps/), [Native badge API](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter/setbadgecount(_:withcompletionhandler:))
